# Design Doc — Safia's & Safaan's Math Dojo

## What this is

A browser-based math practice app shared by two kids, Safia and Safaan: 20 practice levels with auto-generated questions across 5 input types, 56 real-world "SOAR" activities (sourced from NRICH), a Mental Math Gym (a hub of pooled Daily/Random assignments, a stepped strategy coach, and spaced-repetition flash cards) for building fast mental arithmetic, a Safia-only **Number Talks Zone** for conceptual number sense (see [Number Talks Zone](#number-talks-zone)), trophies/badges/streaks/daily bonus for motivation, and a save/load system covering both kids' progress. Each kid is a **racer** with their own scoped level lane, SOAR age band, stars, trophies and Gym state (see [Two racers](#two-racers)); a **Grown-up summary** screen is the one place both appear together. Navigation is a persistent left **rail** on wide screens (Chromebook/desktop/landscape tablet, ≥900px) and falls back to a top strip + bottom tab bar below that — see [Screens & navigation](#screens--navigation). Hinted questions get an interactive, stepped worked example (a drawn column-method grid or a number-strip), not just a line of prose — see [Question engine](#question-engine). Visually it follows the "Turbo Math Design System" — dark teal/graphite surfaces, cyan/coral/amber accents, a racing/dojo motif, a fixed race-photo background, and a "pressed game button" interaction language throughout.

It began as "Safia's Math Kingdom" (hot-pink/purple, princess-themed), was reskinned into the current Turbo Math palette, then most recently rebuilt around the rail shell + two-racer model described here, with the Number Talks Zone added on top as its own Safia-only section. Where history matters to a design decision, it's called out below.

## Two racers

`RACERS` (in `mathdata.js`) defines each kid's slice of `LEVELS` and SOAR band — confirmed with the customer before shipping, since the ranges deliberately overlap (levels 4–8 are shared review/stretch material for both):

```js
const RACERS = {
  safia:  { name: 'Safia',  age: 6, from: 0, to: 8,  band: '3-5'  }, // Counting → Make a Sum
  safaan: { name: 'Safaan', age: 9, from: 3, to: 20, band: '7-11' }, // Carry Addition → Grand Finale
};
```

`activeRacer` (`script.js`) is a plain, un-namespaced pointer (`mathdojo-active-racer` in `localStorage`, default `'safia'`); every *other* piece of state — the 5 core `mathdojo-*` keys and all 9 Gym `tm-mm-*` keys — is namespaced per racer via one helper, `nk(base) → base + '-' + activeRacer` (and `nkFor(base, racerId)` for reading/writing a *specific*, possibly-inactive, racer's keys — used by save/load and the Grown-up summary). `laneLevels(racerId)` is just `LEVELS.slice(from, to)`; no level is ever locked.

`loadRacerState()` (re)populates all 14 of those state variables from the active racer's namespaced keys — called once at boot and again by `swapRacer()`. `swapRacer()` also resets every *transient* (non-persisted) piece of play state (current quiz, Gym nav/play/trick/flash, the dormant drill/sheet/column/tens state) so nothing leaks between racers mid-session, re-renders whatever screen is open, and bounces to Home if the swap happens mid-quiz/result — matching the design prototype's own swap behavior exactly.

**Save/Load is `version: 2`**: `buildSaveBundle()` returns `{version, activeRacer, racers: { safia: {...}, safaan: {...} }}`, each racer's block holding the full 14-field shape. `readRacerBundleFromStorage(racerId)`/`writeRacerBundleToStorage(racerId, data)` read/write one racer's keys directly, without disturbing the *other* racer's live in-memory state — that's how a save can include both racers while only one is "active" in memory at a time. `handleLoadFile` branches three ways: no `version` → legacy bare-progress object, merged into whichever racer is active (unchanged since before racers existed); `version: 2` with a `racers` object → write each present racer straight to storage, then `loadRacerState()` again only if the file touched the currently-active one; anything else (`version: 1`) → the original flat single-profile merge, into the active racer — this is what makes an old, pre-racers save file "just work" against whichever kid has the app open when it's loaded.

## Architecture

**No build step, no bundler, no npm.** Five plain files, loaded as classic (non-module) `<script>` tags, in this order:

```
index.html          screen markup, persistent TopBar + QuickNav chrome
style.css           Turbo Math design tokens + component classes + layout
mathdata.js         content & pure logic: levels, SOAR activities, hints, trophies, badges
mentalmath.js       content & pure logic for the Mental Math Gym — same shape as mathdata.js, zero DOM
script.js           interaction/render/animation layer that drives the DOM
```

This split is deliberate: `mathdata.js`/`mentalmath.js` have zero DOM dependencies (you could run them in Node or a test page with no scaffolding — see [Testing](#testing)), while `script.js` is 100% DOM/interaction code that assumes it's running inside the real `index.html`. Content edits (add a level, tweak a hint, add a SOAR activity, add a fact-family set) touch only the data files; interaction/visual changes touch only `script.js`/`style.css`.

**Why no ES modules:** the app is opened directly via `file://` in addition to being served statically (e.g. GitHub Pages), and `<script type="module">` imports are blocked by CORS under `file://` in Chrome. So the data files expose everything as plain top-level `function`/`const` declarations in global scope rather than `export`s, and `script.js` just uses those names directly — all three files share one script realm, in the same way multiple classic `<script>` tags on one page always have (this matters for how the test suite reaches into that scope — see below). One consequence worth knowing: because `mathdata.js` and `mentalmath.js` share that one global scope, a same-named top-level declaration in both would be a hard parse-time collision, not a silent override — `mentalmath.js`'s own `pick()` helper was renamed `mmPick()` in this repo's copy for exactly that reason (`mathdata.js` already declares a `pick()`).

**Why one small exception lives in `script.js`, not `mathdata.js`:** six SVG/HTML render helpers (`clockFaceSvg`, `formatTime`, `pieSliceSvg`, `barChartHtml`, `shapeSvg`, `lengthBlocksHtml`) are called *by* `mathdata.js`'s question generators but are defined in `script.js`. They're pure presentation (building an inline `<svg>` string), not content, so they belong with the render layer — `mathdata.js` just calls them by name at question-generation time, which works because by the time a level actually runs, both scripts have already loaded.

## Turbo Math Design System

Tokens live at the top of `style.css`, split into three tiers:

1. **Base color scales** — `--teal-950..500`, `--cyan-600..200`, `--coral-600..300`, `--amber-600..300`, plus `--mint-*`/`--red-*` signal colors and `--ink-*` neutrals.
2. **Semantic aliases** — `--bg-app`, `--surface-1/2/raised`, `--text-primary/secondary/muted`, `--color-primary/accent/reward/success/error` (each with a `-hover`/`-press` variant), `--shadow-primary/accent/neutral/reward`. Everything else in the file references *these*, never the raw base scale — that's the seam to change if the palette ever needs adjusting.
3. **Spacing/radius/shadow/type scale** — `--space-1..18`, `--radius-sm/md/lg/xl/pill`, `--shadow-btn-sm/md/lg`, `--ease-snap` (bouncy, for celebratory motion) / `--ease-out` (press feedback), and the type scale (`--font-display` = Lilita One, `--font-body` = Nunito Sans).

**The "pressed game button" mechanic** is pure CSS, no JS:

```css
.btn { box-shadow: 0 5px 0 var(--shadow-neutral); transform: translateY(0);
       transition: transform .08s var(--ease-out), box-shadow .08s var(--ease-out); }
.btn:active { box-shadow: 0 2px 0 var(--shadow-neutral); transform: translateY(3px); }
```

Every pressable class (`.btn`, `.icon-btn`, `.mc-choice`, `.coin-btn`, `.level-tile`, `.menu-card`, `.soar-level-btn`) follows this shape, with the shadow color swapped per variant (`--shadow-primary`/`accent`/`reward`/`neutral`). This intentionally departs from the original React design spec, which tracked a `pressed` boolean in component state via `onMouseDown`/`onMouseUp` — that machinery exists there only because React needs explicit state to re-render. A plain DOM element doesn't: CSS `:active` already fires on press/release for both mouse and touch. The one cross-browser wrinkle is iOS Safari, which only honors `:active` on elements with a touch listener somewhere in the ancestor chain — fixed with a single global no-op listener in `script.js`:

```js
document.body.addEventListener('touchstart', () => {}, { passive: true });
```

## Screens & navigation

**Shell**: `index.html` wraps every screen in `.shell > (.rail | .main | .status-col)`. A single CSS breakpoint at 900px (`@media (min-width:900px)`, no JS width-tracking — simpler than the design prototype's own `state.w` approach, and just as correct since nothing else needs to know the width) toggles between two chrome sets sharing the same 20 screens underneath:

- **≥900px (Chromebook/desktop/landscape tablet)**: `.rail` — a fixed left column with the racer chip (avatar/name/stars, click to `swapRacer()`), 6 nav buttons (Home/Levels/SOAR/Gym/Number Talks/Trophies — Number Talks hidden for Safaan, see [Number Talks Zone](#number-talks-zone)), and a dashed "👪 Grown-up" link pinned to the bottom — plus `.status-col`, a right-hand column shown on Home/Levels/Trophies/the Number Talks Zone (`STATUS_COL_SCREENS` in `script.js`; `showScreen()` toggles `#statusCol`'s inline `display` directly, since the element is always in the DOM): the usual stars/trophy-progress/weak-facts cards everywhere except the zone, which swaps in its own "Why this zone"/"Today" cards instead (same element, different content — see below).
- **<900px (phone/portrait tablet)**: `.topstrip` (racer chip + stars + a back button) at the top of `.main`, and the original sticky-bottom `.quicknav` (now 6 icon-only tabs) at the end of it.

Nineteen screens total (`<div class="screen">` with a `.active` toggle): the original six — `homeScreen → practiceMenuScreen/soarMenuScreen → soarActivityScreen/quizScreen → resultScreen` — plus two redesign-era additions (`trophiesScreen`, `grownupScreen`), `ntScreen` (the Number Talks Zone, one mount point for its own 6-state internal nav — see below), and the Gym's own `gymScreen` plus six dormant children (`drillScreen`, `dailyScreen`, `columnScreen`, `gymResultScreen`, `sheetResultScreen`, `tensScreen` — see [Mental Math Gym](#mental-math-gym)). Flash cards and Learn a trick used to have their own top-level screens (`flashScreen`/`trainerScreen`) too, but the hub redesign folded both into `gymScreen`'s own internal state machine (`gymNav`/`gymHistory`), so those two divs were retired along with the code that rendered into them.

There is no more generic persistent TopBar (no title, no Save/Load — those moved to the Grown-up summary, since they're "grown-up actions, not play actions"). `showScreen(id)` now only manages: the `.active` class, `updateTopBar(id)` (visibility of the narrow top-strip's own back button — hidden on `homeScreen`, `gymScreen` and `ntScreen`, since the Gym and the Number Talks Zone hub each render their own back button internally, visible everywhere else), `setActiveQuickNavTab(id)` (toggles `.nav-item--active` on **every** `.nav-item` sharing a `data-tab`, so the rail and the bottom tab bar are driven by the exact same call), and the status-column visibility/content-swap above. Nested screens without a rail/tab-bar path back (Quiz, SOAR Activity, Grown-up summary) draw their own small inline `←` calling `handleBack()` directly, since on wide screens there's no persistent back button at all — the rail's nav items already switch destinations directly.

`BACK_TARGET` and `TAB_FOR_SCREEN` are flat lookup maps keyed by screen id (now including `trophiesScreen`/`grownupScreen`/`ntScreen`) — every Gym child screen maps back to `gymScreen`, `gymScreen` and `ntScreen` both map back to `homeScreen`, and `grownupScreen` deliberately has **no** `TAB_FOR_SCREEN` entry (it's a pinned rail link, not one of the 6 nav tabs, so nothing highlights while on it — `setActiveQuickNavTab` no longer has a `||'home'` fallback for exactly this reason). `handleBack()` looks up the current screen in `BACK_TARGET`, **except** `gymScreen` and `ntScreen`, which it special-cases to `gymBack()`/`ntBack()` (each its own internal navigation) instead — see [Mental Math Gym](#mental-math-gym) and [Number Talks Zone](#number-talks-zone). `showScreen()` is also the single hook point for tearing down the (dormant) Speed Drill's live timers whenever navigation leaves `drillScreen`.

## Question engine

Every question object carries a `type` (specific, e.g. `carry_add`, `fraction_identify`) and either an explicit `kind` or one resolved via `KIND_BY_TYPE` fallback — `kindOf(q)` in `mathdata.js` is the single dispatch point. Five kinds exist, and `script.js`'s `QUESTION_TYPES` registry is the contract each must satisfy:

```js
QUESTION_TYPES[kind] = {
  inputHtml(q),   // returns the input markup to inject into the question card
  bindEnter(q),   // wires up click/Enter-to-submit handlers
  check(q)        // -> { status: 'empty'|'correct'|'wrong', message }
}
```

kinds: `numeric` (text input), `multiple_choice` (button grid), `coin_picker` (tap-to-select coins with a running total), `compose_pair` (two rows of two numbers), `fact_family` (four rows of `a op b = c`, checked and colored **per row independently** — not all-or-nothing — against the 4 canonical fact permutations of `a`, `b`, `total`).

`generateLevel(id)` → `buildLevel(eqFn, wordPool)` produces exactly 15 questions per level: 7 hinted + 3 unhinted auto-generated equations, then 2 hinted + 3 unhinted hand-written word problems (pulled and shuffled from that level's pool). Most `eqXxx()` generators pick randomly among 2–4 sub-type "flavors" each call (e.g. `eqCompare` rotates through symbol-comparison, true/false, doubles, and near-doubles) — this is where most of the content variety comes from, and it's also why several tests sample a generator many times (`for i in 0..N`) rather than asserting on a single call.

### Hints: a stepped worked example, not a single line of prose

Every hinted question still carries its original `hint` string (plain prose or a pre-baked HTML block — unchanged, never removed), but arithmetic-shaped questions now *also* carry a small literal descriptor, `work`, set alongside it: `{k:'add'|'sub'|'cup'|'cdown', a, b}`, or an array of two such descriptors for the chained two-op word problems (`add_three`/`sub_three`). `work` is chosen by the *numeric shape* of the question, not by which level it sits in — e.g. `eqCarryAdd()` sets `work:{k:'add',a,b}` whenever the ones digits carry, `eqBorrowSub()` sets `work:{k:'sub',a,b}` whenever the ones digit needs to borrow, `eqCounting()`/`eqMissingAdd()`/`eqCompare()`'s true-false and double/near-double branches use `stripSteps`'s `'cup'`/`'cdown'` kinds for single-digit count-on/count-up work, and non-arithmetic categories (money, fractions, logic, shapes, calendar, graphs' non-`graph_diff` branches) set no `work` at all and keep rendering their original prose hint unchanged.

Three pure, DOM-free functions in `mathdata.js` turn a `work` descriptor into an ordered list of steps:

- `columnSteps(a, b, op)` — the column method for two-digit add/subtract, one step per digit column plus a final result step. Handles carry and no-carry addition, and three subtraction shapes (equal tens, no borrow needed, borrow needed) as separate branches, matching exactly how a child would work the problem left-to-right on paper. Every row (carry/top/bottom/result) is padded to the same column count *per step*, computed from that step's own widest row (`Math.max(carry.length, top.length, bot.length, res.length)`) rather than assumed to always be 2 digits — a 3-digit carry result (e.g. `69 + 69 = 138`, reachable via `eqCarryAdd`'s own range) widens to 4 cells only on the step(s) where the extra digit actually appears, keeping every other step's grid at its normal width.
- `stripSteps(kind, a, b)` — a 4-step number-strip ("count up from `a` to `b`" or "count down from `a` to `b`"), rendering a row of chips with the counted-through range highlighted.
- `workSteps(work)` — the dispatcher `renderHintContent(q)` (in `script.js`) actually calls: normalizes `work` to an array (so a single descriptor and a chained pair go through the same path), and concatenates each part's `columnSteps`/`stripSteps` output into one continuous step sequence — this is how a chained problem like `add_three` gets a single continuous Back/Next flow spanning both of its column-method sub-problems, not two separate hint panels.

On the rendering side, `script.js` keeps `hintStep` (reset to 0 every `renderQuestion()`) and re-renders the current step via `renderHintStepHtml()` on ◀ Back / Next step ▶ / ↻ Start again — the answer is never shown before the child reaches the final step, by construction (each intermediate step's `res` row is either blank or shows only the digits already "solved" at that point). Cell colors are plain token names (`'ink'|'amber'|'cyan'|'muted'|'coral'`) resolved to the real `--text-primary`/`--amber-400`/`--cyan-300`/`--text-muted`/`--color-error`-style CSS variables only at render time (`HINT_COLORS` in `script.js`), keeping `mathdata.js` itself free of any DOM or CSS knowledge — the same content/interaction split the rest of the file already follows.

## Mental Math Gym

A separate practice mode for building *speed* at facts a level's untimed quiz doesn't push on. Reached via a Gym card on Home or the QuickNav's 🧠 tab. All of its state (`mmCards`, `mmMisses`, `mmBest`, `mmSets`, `mmSession`, `mmSheet`, `tensRecord`, `gymSpeedRound`, `gymDaily`) is racer-namespaced like everything else — see [Two racers](#two-racers) — so Safia's and Safaan's fact-set picks, mastery, and daily-assignment progress never bleed into each other; nothing in this section's own code changed to make that true, since it already went entirely through the shared `nk()`-wrapped persist functions.

### The hub — three featured cards, not six equal tiles

The hub was redesigned around three destinations plus a quieter secondary tier, replacing an earlier six-same-weight-tile grid that had grown cluttered. Everything below — hub, detail screens, the pooled play flow, Learn a trick, Flash cards, and the grown-up summary — lives inside the one `gymScreen`/`#gymContent` mount, driven entirely by two state variables: `gymNav` (the current internal "screen" name — `hub`/`daily`/`random`/`play`/`trick`/`flash`/`summary`) and `gymHistory` (a stack of prior `gymNav` values). `gymOpen(screen)` pushes and navigates forward; `gymBack()` pops — and, if the stack is already empty, falls through to `showScreen('homeScreen')`, since an empty history means we're at the hub root. Every nested view renders its own `.gym-back` button via `gymDetailHeader()`; the hub root's own back button is always present in the markup but `visibility:hidden` when history is empty (never `display:none`, so the header layout doesn't shift) — the same show/hide idiom the app's outer TopBar back button already uses. Because the Gym now has this self-contained back button, the outer TopBar's own back button is hidden for the whole time the app is on `gymScreen` (see `updateTopBar()`), and `handleBack()` special-cases `gymScreen` to call `gymBack()` instead of the usual flat `BACK_TARGET` lookup.

- **Daily assignment** and **Random mix** — 16 and 12 problems respectively, pooled from whichever fact sets are picked in "Pick what to practise" (`mmSets`, now genuinely wired up — toggling a chip changes both the picked count and the per-set problem breakdown shown on each detail screen, via `gymProblemsPerSet(total, count)` splitting the total evenly with the remainder spread over the first sets). `gymGenProblem(id)` sources each pooled problem from the *real* generators, per set: `tensSheet()`/`columnSheet()` (sampled with repetition via `gymFromPool()`, since those sheets are a fixed 12 items but a pool might need more or fewer) for the `tensOnes`/`carry` sets, `randFact(id)` for the other nine. Daily assignment also carries a **⚡ Speed round** toggle (`gymSpeedRound`, its own `.gym-speed-toggle` click handler calling `stopPropagation()` so it doesn't also open the card) — when on, `gymBuildQueue()` reserves 4 of the 16 slots for quick single-fact recall drawn from a random picked set, splitting the other 12 across the picked-set breakdown instead of 16. The play screen itself (`renderGymPlay()`) is deliberately the simplest input in the app — a native `<input type="number">`, not the shared on-screen keypad — matching the redesign's own prototype exactly for this one flow.
- **Learn a trick** (`gymStartTrick()`/`gymTrick`) — still built on the real `trainerFact()`/`trainerSteps()` from `mentalmath.js`, but redesigned: every step of the fact is shown **stacked from the start** (`gymTrick.doneSteps`), not revealed one at a time or scaffolded away after a clean streak like the previous version — the active step is highlighted (amber border), future steps are dimmed, done steps show their entered answer. A wrong answer (`gymCommitTrickStep()`) clears the entry and flashes "Not quite — try again ✏️" without advancing or revealing the answer — the child stays on the same step. `trainerSteps()`'s step copy was rewritten for plain-language comprehension (the previous "Split the 9 into 8 and…" wording tested badly); step text is still derived from the fact at render time, never stored, so a copy change always reaches an in-progress problem.
- **Flash cards** (`gymStartFlash()`/`gymFlash`) — a fresh 5-card deck drawn from the picked sets every time (no spaced-repetition "due card" revival, unlike the dormant `flashDeck()`-based flow below — the redesign simplifies to a plain fresh draw); grading still calls the real `gradeCard()` so the Leitner boxes (`mmCards`) and the hub's "N% mastered" stat (`mastery(mmCards)`) stay meaningful. Every `add20`/`sub20`/`tensOnes` fact drawn for a flash card is capped at 30 (`cappedFact()` in `mentalmath.js`, `FLASH_CAP_SETS`) via a bounded retry (~40 attempts) plus a safe small-number fallback — enforced in the generator, not by filtering afterwards — so a 7-year-old never flips a card into a three-digit mental sum. `carry` facts are deliberately left uncapped (a two-digit column fact like "68 + 47" is exactly the point of that set).
- **Tens & Ones tally inside the Gym** — the hub's own quiet footer button (`gymOpen('summary')`) still renders `tensReportHtml()`, the same per-strategy tally the dormant Tens & Ones screen's own summary uses (see below) — a shared render function, not a duplicate. This is distinct from the app-level **Grown-up summary** screen described in [Screens & navigation](#screens--navigation), which is reached from the rail's pinned footer link, shows both racers side by side, and owns Save/Load — the two screens answer different questions ("how did today's Tens & Ones strategies go" vs. "how is each kid doing overall").

### The dormant screens — Tens & Ones, Carry & Borrow, Speed Drill, Today's sheet

Tens & Ones, Carry & Borrow and Speed Drill stopped being top-level hub destinations in this redesign — their guided-teaching richness (the base-ten-blocks trading, the live column-arithmetic drawing, the drill's ghost-pace timer) doesn't fit the new Daily/Random pooled-question model, but nothing about that code was removed: `tensScreen`/`columnScreen`/`drillScreen`/`dailyScreen` and every function behind them (`startTens()`, `startColumn()`, `startDrill()`, `startDaily()`/`startSheet()`, `tradeTensBlocks()`, `columnPlan()`'s renderer, the drill's `stopDrillTimers()` cleanup, etc.) are still fully intact, still covered by their existing tests, and still reachable by calling their entry function directly — they are simply no longer linked from any button in the redesigned hub. Only their *generator* functions (`tensSheet`, `columnSheet`, `randFact`/`buildDrill`) are reused by the new hub, for the plain pooled numeric/word problems described above. This was a deliberate choice to avoid discarding a full recently-built feature (Tens & Ones' 5-strategy teaching sheet in particular) over a hub layout change — see the git history around this redesign for the reasoning.

- **Speed drill** (`startDrill()`) — a fixed-length `buildDrill(20, sets, misses)` queue, keypad entry except every 3rd question (`idx % 3 === 2`) which is multiple-choice via `choicesFor()`. No fail state, no time limit — just a live `setInterval` clock and a "ghost" bar showing where a personal-best run would be at the same elapsed time (a linear pace projection, `min(N, elapsed/(best.time/N))`, not a literal replay). Answering auto-advances after a fixed delay (550ms correct / 1400ms wrong) with no manual "Next" tap — the one place in the whole app with a live countdown-driven timer, which is why it's also the one screen `showScreen()` has a special cleanup hook for (`stopDrillTimers()` clears both the clock `setInterval` and the pending auto-advance `setTimeout`, called whenever navigation leaves `drillScreen` and at the moment a drill finishes).
- **Today's sheet** / **Carry & borrow** (`startDaily()`/`startColumn()`) — two resumable, date-seeded practice sheets (`dailySheet()`/`columnSheet()`, both deterministic per `todayKey()` so refreshing mid-sheet doesn't reshuffle it), sharing one `startSheet(kind)`/`nextSheetItem()` pair since their resumability/scoring bookkeeping is identical; only the per-problem renderer differs. **Carry & borrow** is the most visually distinct piece: `columnPlan(problem)` returns an ordered list of guided steps (a leading yes/no step for subtraction — "is the top ones digit big enough?" — then numeric entry steps), each carrying a `reveal` object whose keys (`carry`, `tensNew`/`onesNew`, `resTens`/`resOnes`) the renderer paints directly into a live column-arithmetic drawing (`.column-math`) as the child answers — the borrow/carry sequence isn't hardcoded in the renderer, it's read off whatever `reveal` keys that step happens to send.
- **Tens & ones** (`startTens()`) — the most visually complex sheet, teaching place-value addition/subtraction within 100 via 5 strategies (split the tens, base-ten blocks, number line, round-and-adjust/compensate, column method). `tensSheet(key)` returns a **fixed 12-problem plan** (which strategy/op/regroup-or-not each problem is, in a set order — only the actual numbers are date-seeded, unlike the drill/flash pools which resample every visit) so every kid sees the same strategy progression on a given day. `tensSteps(it)` returns that problem's ordered `{text, answer}` blanks — split/line/compensate/blocks-subtraction reveal their final answer on the last step; blocks-addition and column carry structured `reveal` data (`resTens`/`resOnes`, plus `carry`/`tensNew`/`onesNew` for column) the renderer paints into a live base-ten-blocks or column-arithmetic drawing, the same `reveal`-driven idiom Carry & Borrow already uses. Base-ten-blocks problems that need regrouping start **gated** (`tensBlocks.gate`) — the keypad stays hidden until the child taps `tradeTensBlocks()` to trade ten loose cubes for a rod (addition) or manually removes blocks down to the target via `takeTensRod()`/`takeTensCube()` (subtraction) — forcing the physical model before the abstract answer. One screen (`tensScreen`/`#tensContent`) hosts three sub-views gated by a `tensView` state var (`'play'`/`'result'`/`'report'`), mirroring how the original React prototype kept player/result/summary as one component's internal states rather than three separate screens. `tensReportHtml()` — the strategy tally shared with the redesigned hub's "👪 Grown-up summary" — tallies `tensRecord.log` (one `{strategy, ok}` entry per solved problem, `ok` meaning solved with zero wrong steps) per strategy and flags any strategy under 75% clean as worth another look.

Adaptivity is shared across drill and flash cards: every missed fact increments a `tm-mm-misses` counter keyed by fact id (`set:display`); a correct answer decrements it (deleted once it hits 0). `buildDrill()` weights its random draw toward fact *sets* with more misses, and the Home screen's "🎯 Practice These" panel (`renderWeakFactsPanel()`) surfaces the worst offenders via `weakFacts(misses, 6)` — this is the same `#patternSummary`/`#patternTags` panel the original app shipped with, just now actually wired up (see [Known quirks](#known-quirks) history below).

## Number Talks Zone

A **Safia-only** section targeting a specific gap flagged by her Winter 2026 MAP Growth results (84th percentile achievement, 56th percentile growth — a sign of coasting on procedures rather than building flexible number sense): five short activities that build conceptual understanding instead of more drill. Content and generators come from `design_handoff_number_talks_zone/`, ported verbatim into `mathdata.js`; the shell/interaction layer is new.

**Why Safia-only, and how that's enforced**: the gate is `activeRacer==='safia'`, checked live, not a stored flag — `showNumberTalks()` bounces to Home immediately if Safaan is active, and `renderRacerChips()` (already called on boot/swap/every star update) hides the rail/quicknav nav buttons (`#railNtNav`/`#quicknavNtTab`) the same way. `swapRacer()` folds `ntScreen` into the same "bounce Home" check it already used for Quiz/Result, since swapping away from the zone always means Safaan just became active. There's no separate "is this feature enabled" flag anywhere — one live check, applied at every entry point, is the whole gate (see the regression suite pinning this).

**Shell**: one mount point, `ntScreen`/`#ntContent`, with its own tiny internal state machine — `ntNav` (`'hub'|'numberTalks'|'patterns'|'problems'|'realWorld'|'games'`), `ntOpen(screen)`/`ntBack()` — the same idiom as the Gym hub's `gymNav`/`gymOpen`/`gymBack()`, just without a history stack, since there's only ever one level of nesting (hub, then exactly one activity). The hub's 5 tiles reuse `.gym-card`/`.gym-card--primary|accent|reward` as-is (no parallel "MenuCard" component was built); each activity's back button reuses `.gym-back`. The status column shows throughout the zone (not just Home/Levels/Trophies like everywhere else) but with different content — see [Screens & navigation](#screens--navigation) and `showScreen()`'s `isNt` branch, which swaps `#statusStarsCard`/`#statusTrophyCard`/`#patternSummary` out for `#ntWhyCard` (Safia's real percentiles, static) and `#ntTodayCard` (`ntStats`' live total, via `renderNtStatusColumn()`).

**The five activities** (`mathdata.js` generators, `script.js` render/handlers — `renderNt*()`/`nt*Check()` per activity):
- **Number Talks** (`ntSubmitWay()`) — type two numbers that sum to the current target (`NT_TARGETS = [8,10,12,15,20]`); a wrong sum or a reversed-order duplicate (`[a,b].sort().join('-')` as the dedup key) is rejected with feedback but keeps whatever the child typed, so they can adjust rather than retype; "🔄 New number" clears the "ways found" list and picks a new target. Self-paced — no timer.
- **Patterns** (`ntGenPattern()`) — 50/50 repeating (an emoji unit tripled then sliced to 4, multiple-choice) or growing (constant-step arithmetic, numeric input). Repeat-mode always auto-advances 1.3s after a pick, right or wrong; grow-mode only auto-advances (1s) on a **correct** answer — a wrong one waits for a retry. `ptStreak`-equivalent (`ntPatternStreak`) resets on any miss.
- **Problem Solving** (`NT_PROBLEMS`, a fixed 6-item pool with 2 named strategies each) — Check/Next, self-paced. "🔀 Try it another way" only appears after a correct check and reveals both strategies at once (`ntToggleStrategies()`), not sequentially.
- **Real-World Math** (`ntGenRealWorld()`) — randomly money, time, or measurement, multiple choice; the returned object carries its own `display(v)` formatter (e.g. `+'¢'`, `+' in'`) so the tile labels and the "it was X" callout format identically without the renderer needing to know which kind it got. Auto-advances (1.3s correct / 1.7s wrong).
- **Pit Crew Games** (`ntGenGame(streak)`) — a missing-number equation (`? + 5 = 12` style, blank position random); the number range widens with streak length (capped at +5 steps), so it gets harder the longer the child stays correct. Auto-advances (0.9s correct / 1.5s wrong).

Every auto-advancing activity's `setTimeout` callback re-checks `ntNav==='<screen>'` before re-rendering — if the child has already backed out to the hub (or elsewhere) before the delay elapses, the stale timer is a no-op instead of silently overwriting whatever's on screen next.

**Persistence**: only the completed-activity tally survives reload — `ntStats = {talks,patterns,problems,realWorld,games}`, its own racer-namespaced key (`mathdojo-nt-stats`) and its own `persistNt()`, same rationale as `persistGym()`/`persistTens()` being split out from `persistAll()` (see [Persistence](#persistence)). Everything else (current pattern/problem/game, streaks, "ways found") is transient, reset in `swapRacer()` like the Gym's own play state.

## Game feel: streaks, trophies, badges, confetti

- **Streak**: increments on each correct answer, resets on any wrong answer. Drives the QuizStatRow's streak pill, a floating "🔥 N in a row!" badge (shown once streak ≥ 2), and confetti volume.
- **Trophies** (`TROPHIES` in `mathdata.js`, 16 entries): each has a `check(newStarTotal, progress) → boolean`, called after every scoring event. `pendingMilestones` is a real queue — `showMilestone()` pushes, `showNextMilestone()` shifts and displays one at a time via the modal, `closeMilestone()` drains the next after its close animation. This matters because a single scoring event can satisfy several trophy thresholds simultaneously (e.g. going from 0→20 stars in one jump trips `first_correct`, `five_stars`, `ten_stars`, and `twenty_stars` all at once) — the queue is what stops all but one from being silently dropped. Earned trophies render as generated `.trophy-tile--earned` tiles on the dedicated Trophies screen (`renderTrophyShelf()` → `#trophiesGrid`), not the old id-per-trophy hardcoded shelf.
- **Badges** (`BADGES_DEF`, 10 entries): simpler derived-from-`progress` checks (e.g. "complete both `time` and `calendar`"), recomputed wholesale by `checkBadges()` after anything that could affect them (`checkBadges()` itself only computes and persists the `badges` data now — rendering the 10 generated `.trophy-tile`s into `#badgesGrid` is `renderTrophyShelf()`'s job, called separately, same as the trophy grid above).
- **Daily bonus**: one `+3` star claim per calendar day, gated by comparing `new Date().toDateString()` against the last-claimed date in `localStorage`, namespaced per racer (`nk('mathdojo-lastbonus')`) like everything else — see [Two racers](#two-racers).
- **Confetti**: canvas-based (`launchConfetti(n)` + `requestAnimationFrame` loop), not DOM-node-per-particle — cheaper for the larger bursts (level completion, trophy unlock).
- **One-shot only, no ambient loops**: every celebration (correct/wrong pop, milestone modal, the result screen's star-drop, confetti) is a one-shot animation triggered by an event. The redesign removed the app's four `infinite`-looping CSS animations — the mascot's float (the mascot itself was removed, see [Screens & navigation](#screens--navigation)), the old daily-bonus card's pulse (folded into the Today card), the old trophy shelf's glow (moot once Trophies became its own tile grid), and the result card's pulse — on the judgment that a screen that's just sitting there being looked at shouldn't also be animating at it.

## Persistence

Core app state lives in `localStorage` under a `mathdojo-` prefix: `progress`, `soar`, `trophies`, `badges`, `stars`, `lastbonus`. `persistAll()` writes those five in one call and is used anywhere more than one of them can change together (finishing a level, completing a SOAR activity, loading a save file).

The Mental Math Gym uses its own prefix, `tm-mm-`, and its own `persistMM()` function: `cards` (Leitner boxes), `misses` (the adaptivity counter), `best` (drill personal-best `{time, score}`), `sets` (which fact sets are toggled on), `session` (a counter used to compute which flash cards are "due"), `sheet` (`{key: <today's date string>, daily:{done,correct}, column:{done,correct}}`, reset whenever `key` doesn't match today — that's what makes the two sheets resumable-but-daily). It's a separate function rather than folded into `persistAll()` on purpose: Gym state changes on nearly every keystroke/flip/answer, far more often than the five `mathdojo-*` fields (which only change at level/activity completion boundaries), and keeping them separate means a test asserting `persistAll()`'s exact field count doesn't have to know about the Gym at all.

Tens & Ones has its own key (`tm-mm-tens`) and its own `persistTens()` function, kept separate from `persistMM()` for the same reason `persistMM()` is kept separate from `persistAll()` — one more independent save cadence, one more field a `persistMM()`-field-count test doesn't need to know about. It stores `tensRecord`: `{key: <today's date string>, done, correct, log: [{strategy, ok}, ...]}`, reset whenever `key` doesn't match today.

The Gym hub redesign added two more fields, its own `persistGym()`, and its own two keys for the same reason: `tm-mm-speed` (`gymSpeedRound`, the Daily assignment card's ⚡ toggle) and `tm-mm-assign` (`gymDaily`, `{key, done, correct}` for the new Daily assignment — distinct from the dormant `mmSheet.daily` above, which still belongs to the old, unlinked "Today's sheet" screen). `gymNav`/`gymHistory`/`gymPlay`/`gymTrick`/`gymFlash` are deliberately **not** persisted — like the redesign's own React prototype, the Gym's in-progress navigation and play state resets on reload; only completion counts (`gymDaily`) and settings (`mmSets`, `gymSpeedRound`) survive.

The Number Talks Zone follows the same pattern once more: its own key (`mathdojo-nt-stats`) and its own `persistNt()`, storing only the completed-activity tally `ntStats = {talks,patterns,problems,realWorld,games}`. Everything else about the zone (current pattern/problem/game, streaks, "ways found") is transient, same rationale as the Gym's own unpersisted play state — see [Number Talks Zone](#number-talks-zone).

**Every key above is racer-namespaced.** All 15 fields named in this section — the five `mathdojo-*` fields plus `lastbonus`, the nine `tm-mm-*`/Gym fields, and `ntStats` — are written and read through `nk(base)`/`nkFor(base, racerId)`, which append `-<racerId>` to the literal key. `activeRacer` itself is the one exception: it's the un-namespaced pointer that says *which* racer's keys to read, stored bare at `mathdojo-active-racer`. See [Two racers](#two-racers) for the full model (`loadRacerState()`, `swapRacer()`) — this section only covers what each field means and how often it's flushed, which didn't change.

**Save/Load** exports/imports *everything*, for *both racers at once* (`version:2`): `buildSaveBundle()` → `{version:2, savedAt, activeRacer, racers:{<id>:{...the same five `mathdojo-*` fields, six Gym fields, `tensRecord`, `gymSpeedRound`, `gymDaily`, and `ntStats` as before...}}}` for each of `safia`/`safaan` (Safaan's bundle carries an `ntStats` field too, even though he can't reach the zone — it's just whatever zero/stale value his own key holds, harmless and simpler than special-casing the bundle shape per racer). `handleLoadFile` branches three ways: no `version` field → legacy bare-`progress` object, merged into whichever racer is currently active (unchanged from before racers existed); `version:2` with a `racers` map → write each racer's bundle straight to its own namespaced keys via `writeRacerBundleToStorage()`, only reloading live in-memory state via `loadRacerState()` if the active racer was among the ones touched; anything else (`version:1`, the original flat single-profile shape) → the original field-by-field merge logic, applied to whichever racer is currently active — this is what makes a save file from before the two-racer redesign existed "just work" when loaded today.

## Testing

See [`tests/`](tests/) and its own comments for specifics; the shape of the split:

- **Unit** (`tests/unit.test.js`, `tests/unit-mentalmath.test.js`) — `mathdata.js` and `mentalmath.js` alone, no DOM. The six SVG helpers `mathdata.js` calls are stubbed with minimal same-signature stand-ins (real coverage of those lives in integration tests) so generator-structure assertions (question counts, valid `kind`, exactly-one-correct-choice, sheet sizes, date-seeded determinism, `columnPlan`/`tensSteps` step-answer reconstruction, the fixed 12-problem `tensSheet` strategy plan, the flash-card 30 cap on `cappedFact()`, the rewritten `trainerSteps()` copy, etc.) don't need the real app running. The stepped hint engine gets its own suite here too — `columnSteps`/`stripSteps`/`workSteps` — covering carry/no-carry and same-tens/no-borrow/borrow reconstruction, the 3-digit-result edge case (`69+69=138`), chaining two descriptors into one continuous sequence, "no answer shown at step 0", and `workSteps(undefined)` returning `null` for non-arithmetic questions. The Number Talks Zone generators get their own suite too — `ntGenPattern`/`ntGenRealWorld`/`ntGenGame` reconstructed and re-verified (equation validity regardless of which part is blanked, difficulty widening with streak, the answer always present among the options), plus `NT_PROBLEMS`/`NT_TARGETS` shape checks.
- **Integration** (`tests/integration.test.js`) — the *real* `index.html`/`style.css`/`mathdata.js`/`mentalmath.js`/`script.js`, loaded in a same-origin iframe and driven like a player would: click through screens, answer all 5 question kinds, complete a level, complete a SOAR activity, save/load (including the `version:2` two-racer bundle shape), exercise the redesigned Gym hub (its own back-button history stack, a chip toggle changing the Daily assignment breakdown, an empty selection dimming Start, the speed round toggle, playing Daily/Random to completion, Learn a trick's wrong-answer-doesn't-advance rule, Flash cards' 5-card cap), confirm the dormant Speed Drill/Today's-sheet/Carry & Borrow screens still work when called directly, and — for Tens & Ones specifically — one problem of each of its 5 strategies, including the base-ten-blocks trade gate and the column method's carry/borrow reveal. Suites specific to prior redesigns: **two racers** (swapping racers re-scopes Levels/SOAR/stars/trophies/Gym independently, with no bleed between them), **keyboard play** (a real `keydown` Enter event checks the answer, then advances), and the **stepped hint panel** (opening a hint renders step 0 without the answer, and Next/Back/Restart move through the sequence correctly). The **Number Talks Zone** suite covers the Safia-only gate (nav hidden and `showNumberTalks()` a no-op for Safaan), hub → activity → back navigation, each of the 5 activities' correctness (Number Talks' duplicate/wrong-sum rejection, Patterns' asymmetric auto-advance — repeat mode always advances, grow mode only on correct — Problem Solving's post-correct-only strategy reveal, Real-World's and Games' auto-advance/scoring), the swapped-in status-column content, and the `ntStats` save/load round trip.
- **Regression** (`tests/regression.test.js`) — pins specific decisions and previously-fragile behaviors by name (the `mathdojo-*` key rename — now also racer-namespaced — the trophy milestone queue, per-row fact-family checking, the design tokens, the unified `.nav-item`/`#topStripBack` navigation targets, the Number Talks Zone's Safia-only gate surviving a mid-session racer swap, and its `mathdata.js` content staying DOM-free) so they can't silently drift back.

**Why integration/regression tests use `iframe.contentWindow.eval(...)` instead of `iframe.contentWindow.someGlobal`:** most app state (`progress`, `currentStreak`, `LEVELS`, `TROPHIES`, ...) is declared with top-level `let`/`const`. Unlike `var` or function declarations, `let`/`const` at script scope do **not** become properties of the `window` object — they're only visible to code evaluated *inside that same realm* (exactly like typing into that page's own DevTools console). `frame.contentWindow.eval(code)` runs as indirect eval in the iframe's global scope and *can* see those bindings; a plain property read from the parent can't. Calling an exported function (`appWin().startLevel(...)`) works fine either way since function declarations do attach to `window` — the tests just use `eval()` uniformly for consistency.

Run the suite by opening `tests/index.html` in any browser (zero dependencies), or headlessly via `python3 tests/run.py` (spawns its own static server + headless Chrome; needs `pip install websockets` for that one optional CLI wrapper only).

## Known quirks (intentionally left as-is)

- `showSoarMenu()` now filters to an **exact match** on the active racer's own band (`'3-5'` for Safia, `'7-11'` for Safaan) — no fallback bucket, no sticky headers, matching the redesign's own two-band SOAR data. Activities authored under the other three age strings (`'5-7'`, `'5-11'`, `'9-14'` — including `nim7`/`gotIt`'s `"5-14"`) are consequently unreachable by either racer. This is a deliberate simplification carried over verbatim from the design prototype, not an oversight — see [Two racers](#two-racers).

## History: the retired `mistakePatterns` panel

Earlier versions of this app shipped a `mistakePatterns`/`updateMistakePatternsDisplay()` mechanism and a Home-screen "🎯 Practice These" panel that nothing ever actually wrote to — pure vestigial dead code from a prior iteration. When the Mental Math Gym's adaptivity tracking (`mmMisses`, keyed the same way — by fact id) needed a place to surface its weakest facts, that dead panel was the obvious real home for it rather than adding a second, competing "practice these" UI: `mistakePatterns` and `updateMistakePatternsDisplay()` were deleted outright, and `renderWeakFactsPanel()` now drives the exact same `#patternSummary`/`#patternTags` DOM slot and `.pattern-tag` CSS from `weakFacts(mmMisses, 6)` instead.
